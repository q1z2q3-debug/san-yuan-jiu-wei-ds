## 二、问题清单

### P1【中·文档一致性】症状数量不一致：说明书写 60 项，实际 75 项
- 现象：使用说明 §三、§四、§五 三处均写"60 项症状/体征"，data.js 实际 8 组共 **75 项**。
- 证据：`grep` 统计 `symptomGroups`：寒热9 + 头身胸腹16 + 饮食二便12 + 睡眠情志7 + 形体皮肤6 + 舌象8 + 脉象11 + 病程情境6 = 75。
- 影响：文档口径与产品不一致，验收、测试用例、对外介绍均失真。
- 修复方向：以实际数据为准修订使用说明（推荐），或裁剪症状集到 60（不推荐，丢失信息）。

### P2【高·医学安全】"表虚自汗"硬拦截失效
- 现象：症状"自汗恶风"带 `tag:"表虚"`，且麻黄汤/四逆汤/汗法 etc. contra 均写"表虚自汗忌用"，但该 tag **从未传入引擎**。
- 定位：app.js `runInference()` 构造 ctx 时只传 `tags: UI.tags.bagang`（八纲名），八纲列表（阴/阳/表/里/寒/热/虚/实）中没有"表虚"；engine.js `patternFlags.biaoxu = ctx.tags.includes("表虚")` 恒为 false。
- 验证：表虚+太阳病场景（自汗恶风/脉浮/恶寒）S=1,2,0,1,1,2,0,1,2，麻黄汤 **未被硬拦截**（score -2，处于 passed 候选）。
- 影响：与使用说明「证候禁忌硬拦截 / 算法透明化」承诺直接矛盾；表虚自汗者误用麻黄汤发汗属中医禁忌，存在安全风险。
- 修复方向：在 ctx 增加 `symTags`（由症状 tag 聚合），patternFlags.biaoxu 读取 `symTags`/八纲中的"表虚"；同时把症状特殊标签体系接入该路径。

### P3【高·承诺缺失+安全】配伍审查未含"建议加味后的全方复查"
- 现象：使用说明 §四 明确写"配伍审查…**含建议加味后的全方复查**"，但 engine.js `run()` 中 `compat: checkCompat(herbs, ctx)` 只查原方（jun/chen/zuo/shi），不含 `advice` 列出的药。
- 验证：少阳+阳虚场景（寒热往来/胸胁胀满/恶心呕吐/腹痛喜温喜按/口淡不渴）S=0,1,0,0,1,0,0,0,1 → 首推小柴胡汤，加减建议含附子；原方 compat 仅提示半夏毒性；模拟"原方+全部加减药"后才会出现附子大毒提示。
- 影响：按 UI"加减思路"加药后可能引入十八反/畏恶/妊娠/毒性风险，而报告显示"✔ 审查通过"，给用户错误安全感。
- 修复方向：run() 中对每首推荐方计算"原方+建议加味药"并做全方 checkCompat，UI 展示"原方审查 + 全方（含加减）审查"两段日志。

### P4【高·医学安全】十八反对"附子（乌头类）+"识别失效
- 现象：附子属乌头类，经典十八反"半夏反乌头类"，但 checkCompat(['半夏','附子']) 不产生「反」级提示，仅各自毒性提示。
- 定位：data.js `contra.shibaFan` 中乌头条目书为 `a:"乌头"/"川乌"/"草乌"`，**未含"附子"**；engine `has(n)` 按字符串包含匹配，"附子"与"乌头"互相不包含 → 不命中。
- 验证：`Engine.checkCompat(['半夏','附子'])` 输出仅两条毒性提示，无 反/恐。
- 影响：加味建议若含附子+半夏（临床常见组合，也恰恰是最需警示的组合），算法无法发出十八反警报，与 §七「对十八反…设置算法级硬拦截」承诺不符。
- 修复方向：shibaFan 增加 a:"附子"（同乌头/川乌/草乌组）；或在 checkCompat 中建立"附子→乌头类"别名映射；同步保证全方复查（P3）后该检查真实生效。

### P5【中·推荐质量】症状 tag 未透传导致证候互证/指征检测失效
- 现象：engine.scoreFormulas 对"补阳还五汤"判断血瘀指征时读 `(ctx.symTags||[]).includes("瘀")`，但 ctx 无 symTags 字段，恒为空数组 → 即使已选 4 个瘀血症状（刺痛固定拒按/面色晦暗/舌紫暗有瘀斑/脉涩结代，均 tag:"瘀"）仍打"血瘀指征不足"警告。
- 验证：瘀血四症 S=1,1,0,1,1,0,0,1,1，补阳还五汤 score=-7.5 且 warns 含"血瘀指征不足（无瘀血症状/体征支持）"。
- 影响：典型血瘀证（尤其气虚血瘀型适合补阳还五汤者）被错误降权，推荐排序失真。
- 修复方向：与 P2 一并解决——ctx 增加 symTags 聚合症状 tag（瘀/寒/热/虚/痰湿/湿热/气郁/表虚/表实/少阳等），让症状级证据进入引擎。

### P6【低·体验】中和态（E=0）仍渲染 Top-3 治疗方
- 现象：空输入/纯平和质场景 S=111111111、E=0，Top-3 为 逍遥散(0)/血府逐瘀汤(-3)/小柴胡(-3.5)。UI 已有"无需药物干预，下列推荐仅供参考"提示层，故非错误，但评分 0 的"治疗方"出现在处方语境下仍显机械。
- 修复方向：E=0 时推荐卡改为"中和态无需干预"专卡或仅保留养生提示，不渲染方剂评分排行。

### P7【低·表达】迁移路径文案固定"经中介通道1过渡"
- 现象：buildPath 每步 `why` 为固定模板（"升发X，经中介通道1过渡"/"收敛X，经中介通道1过渡"），对 2→1（收敛回中介）与 0→1（升入中介）语义无区分；多步路径无层级递进说明。
- 修复方向：按 from/to 生成语义文案（0→1：恢复中介通道；2→1：收敛回到中介；跨层级步骤补充"内核→动力→表达"的递进原因）。

### P8【低·展示】状态迁移总览战略方向仅显示吸引子名
- 现象：renderResult "状态迁移总览"只写"战略方向：XX吸引子"，未展开该吸引子的场景/判别条件/切换前提/风险，也未展示宏观标签先验加成明细。
- 修复方向：在该卡内补充 attractor.info（scene/cond/switchPre/risk）与标签先验明细，保持"可解释"承诺一致。

## 四、改进建议（v1.1 修复优先级）

1. **先修 3 个高风险项（P2/P3/P4）**：三者共享一条根因链路——"症状 tag → ctx.symTags → 证候互证与禁忌判定"，建议在引擎入口统一补齐症状级证据接入；P4 单独补 shibaFan/别名映射；P3 单独改 run() 全方复查 + UI 双段日志。
2. **同步修复 P5**（与 P2 同根因，成本极低）。
3. **修订使用说明 P1**：症状数 60→75，其余数据口径（66 味药、14 方、11 分栏）已核对无误。
4. **体验项 P6/P7/P8**：E=0 专卡、路径文案语义化、迁移总览补详情，均可在 v1.1 一并完成。
5. **工程验证项（非源码缺陷）**：build.sh 依赖 `$ROOT/android/sdk`（build-tools 35.0.0 / platforms android-34），当前环境无 SDK，需补齐后才能真正产出 APK 并验证签名与包体 54KB 口径。
